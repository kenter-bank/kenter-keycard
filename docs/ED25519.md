# Ed25519 signing

kenter-keycard adds pure Ed25519 (RFC 8032) signing to the Keycard applet, next to the existing
secp256k1 functions. It is built for Stellar (SEP-0005 / SLIP-0010) but is not specific to it.
This document describes how it works and why, the wire interface, and what the card platform must
provide. The code is `src/main/java/im/status/keycard/Ed25519.java`.

## Approach: no software point arithmetic

Java Card 3.0.x has no native EdDSA, and a byte-oriented software implementation of Edwards curve
arithmetic is far too slow on card CPUs. `Ed25519.java` uses the approach of
[dufkan/JCEd25519](https://github.com/dufkan/JCEd25519) and JCMathLib instead:

1. **Scalar multiplication on the native EC engine.** edwards25519 is birationally equivalent to a
   short-Weierstrass curve, Wei25519 (see the RFC 9380 appendix and the JCMathLib constants). The
   map preserves the group, so `s·B` can be computed by the card's EC hardware with custom curve
   parameters, the same way the applet computes secp256k1 points:
   `KeyAgreement.ALG_EC_SVDP_DH_PLAIN_XY` with a private key carrying the Wei25519 domain
   parameters (`Ed25519.setCurveParameters`). The cofactor is set to 1: JCOP4 P71 rejects 8 on this
   curve, and `ALG_EC_SVDP_DH_PLAIN_XY` does not use the cofactor, so the result is the same.
2. **Map back to Edwards and compress.** With `u = x_w − A/3` (the Montgomery x-coordinate,
   `A = 486662`), the Edwards coordinates are `ed_x = C·u/y_w` and `ed_y = (u−1)/(u+1)`, where
   `C = sqrt(−(A+2))`. The encoded point is the 32-byte little-endian `ed_y` with the parity of
   `ed_x` in the top bit (`Ed25519.encodePoint`).
3. **Modular arithmetic through keycard-math and one RSA operation.** Additions, subtractions and
   multiplications mod `p = 2^255−19` and mod the group order `L` use `BigNumberMath`
   (`crypto.bigMath`). The two modular **inversions** per point encoding use Fermat's little
   theorem, `x^(p−2) mod p`, computed as a single raw RSA operation (`Ed25519.modInv`): a 512-bit
   `RSAPrivateKey` whose modulus is `p` zero-padded to 64 bytes and whose exponent is `p−2`, behind
   `Cipher.ALG_RSA_NOPAD`. JCOP4 P71 refuses 256-bit RSA keys and rejects the padded modulus on a
   public key, so this is JCMathLib's `RSA_RESIZE_MOD` configuration for that chip.

All curve constants are embedded in `Ed25519.java`. They satisfy the curve equation,
`3·(A/3) ≡ A` and `C² ≡ −(A+2) mod p`, and `Ed25519ProbeTest` re-checks the base point against the
curve equation on every run.

## Signing (RFC 8032, pure Ed25519, no prehash)

`Ed25519.signHash` signs a **32-byte message**. For Stellar that is the SHA-256 of the transaction
signature payload, computed by the host; the card treats it as the message `M`.

1. Expand the 32-byte secret: `h = SHA-512(secret)`; clamp `h[0..31]` (little-endian) into the
   scalar `s`; `prefix = h[32..63]`. The clamped scalar is reduced mod `L`. That changes neither
   the public key nor the signature, and keeps it a valid input for the EC engine.
2. `A = encode(s·B)`, the public key, recomputed for each operation. Nothing is cached across
   commands.
3. Deterministic nonce `r = SHA-512(prefix ‖ M) mod L`. No on-card randomness is used, so a weak
   RNG cannot cause nonce reuse.
4. `R = encode(r·B)`; challenge `k = SHA-512(R ‖ A ‖ M) mod L`.
5. `S = (k·s + r) mod L`; the signature is `R ‖ S`, both little-endian as RFC 8032 specifies.

`BigNumberMath` works big-endian; byte order is flipped only at the RFC 8032 boundaries
(`reverse` / `reverseInto`). The same key and message always give the same signature.

## Keys and SLIP-0010 derivation

ed25519 has no BIP32-style public derivation. SLIP-0010 defines the ed25519 variant:
**hardened only**, `I = HMAC-SHA512(chain, 0x00 ‖ key ‖ index)`, with the master pair from
`HMAC-SHA512("ed25519 seed", seed)`.

- The applet never stores the raw seed, so the SLIP-0010 master key and chain code are computed
  when a BIP32 seed is loaded (`loadSeed`, reached from GENERATE KEY and from LOAD KEY with a seed)
  and kept in dedicated persistent fields. They are wiped by REMOVE KEY and FACTORY RESET, and
  cleared when a plain TLV key pair or a non-BIP32 seed is loaded. Without them, Ed25519 SIGN and
  EXPORT KEY return `6985`.
- Derivation runs on card at SIGN and EXPORT KEY time (`Ed25519.slip10Derive`). A path with any
  non-hardened element is rejected with `6984` (`SW_DATA_INVALID`), the same status a failed BIP32
  derivation returns.
- The empty path (the master key itself) is rejected with `6A80`. The master key is the same in
  the main and duress trees (below), so allowing it would let a duress session sign with the real
  master key. Stellar never uses `m` itself.
- The Stellar account path (SEP-0005) is `m/44'/148'/n'`. The test suite reproduces SEP-0005 test
  vector 1 and SLIP-0010 test vector 1 on card.

### Duress PIN

The duress PIN derives a separate, decoy set of Ed25519 keys, as it does for BIP32. Its chain code
is `SHA-256(master chain code)`, computed at seed load; the master key is shared. The chain code is
chosen from the active PIN at each SIGN and EXPORT KEY, so the two cannot fall out of step. The same
path gives a different key under each PIN.

## Wire interface

Both commands run inside the secure channel and need the PIN verified, exactly as the secp256k1
variants do.

- **SIGN** (INS `0xC0`), P1 = `0x01` (derive from master), P2 = `0x01` (`SIGN_ED25519`).
  Data: 32-byte message ‖ derivation path (4-byte big-endian elements, all hardened).
  Response: `A0 81 64 { 80 20 <Ed25519 public key>, 88 40 <R ‖ S> }`.
  This is the secp256k1 template shape; the public key is 32 bytes instead of 65, and the
  signature uses the raw 64-byte signature tag `0x88` that the Schnorr path also uses.
- **EXPORT KEY** (INS `0xC2`), P2 = `0x03` (`EXPORT_KEY_P2_ED25519_PUBLIC`).
  Data: derivation path. Response: `A1 22 { 80 20 <Ed25519 public key> }`.
  Only the public key can be exported. The Stellar strkey ("G…" address: version byte, CRC16,
  base32) is encoded by the host.

The Cash applet is unchanged from upstream and signs secp256k1 only. A second Ed25519 instance would
not fit a J3R200's transient RAM next to the Keycard applet, and the Cash applet signs without a PIN
or secure channel, which is not acceptable for a Stellar key.

All existing secp256k1, ECDSA and Schnorr behaviour and the secure channel are unchanged.

## Platform requirements

- `KeyAgreement.ALG_EC_SVDP_DH_PLAIN_XY` (Java Card 3.0.5) with custom Fp curve parameters.
- Raw RSA (`ALG_RSA_NOPAD`) with a 512-bit private key, a zero-padded modulus and an arbitrary
  exponent. This is the one platform-dependent piece of the design. `Ed25519ProbeTest` guards it
  with edge cases, including results with leading zero bytes, and the hardware probe in `probe/`
  checks it (and the alternatives) on a real card.
- SHA-512 (`Crypto.sha512`) and HMAC-SHA512 (native, or the applet's software fallback).
- `keycard-math` (`BigNumberMath`): `modAdd` / `modSub` / `modMul` / `modRed` with arbitrary moduli.

Memory: one transient work buffer of 481 bytes (`CLEAR_ON_DESELECT`), one transient EC private key
and one persistent 512-bit RSA private key, plus 96 persistent bytes in the Keycard applet for the
SLIP-0010 master key, its chain code and the duress chain code.

## Simulator

The jcardsim submodule points at a fork that carries the fixes this code needs in the simulator: transient EC private key types, APDU buffer bounds for maximum-length responses,
EC point on-curve validation, and raw `ALG_RSA_NOPAD` that behaves as a card does (arbitrary-exponent
modPow, where the stock BouncyCastle engine rejects both the e=2 squaring and the e=p−2 inversion).
`Ed25519ProbeTest` exercises each primitive directly against the simulator (native XY scalar
multiplication on Wei25519, modMul and modRed mod L, the RSA inversion) and cross-checks every
result with BigInteger and BouncyCastle. `StellarM4Test` signs a real Stellar transaction on card
and verifies it with the Stellar Java SDK.

## Security notes

- Deterministic nonces (RFC 8032): signing does not depend on the RNG.
- The expanded secret, scalars, nonce and all intermediates live in the transient work buffer,
  cleared on deselect. The SLIP-0010 master is persistent by necessity and wiped on key removal.
- Side channels: the native EC engine applies the platform's countermeasures to the scalar
  multiplications, as it does for secp256k1 signing. The `BigNumberMath` field arithmetic in point
  encoding works on values derivable from the public result point. The exception is
  `S = k·s + r mod L`, which handles secrets in software, the same exposure class as the existing
  BIP340 Schnorr code. `BigNumberMath` has not been reviewed for secret-dependent timing.
- Invalid input: non-hardened path elements and the empty path are rejected; the PIN and
  secure-channel requirements for SIGN and EXPORT KEY are the same as for secp256k1.
